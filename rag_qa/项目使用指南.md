## 2. 当前工程版怎么运行

### 2.1 运行模式总览

| 模式 | 入口 | 主要依赖 | 适用场景 |
| --- | --- | --- | --- |
| 工程联调（推荐） | `../start_edurag.bat` / `../start_edurag.ps1` | 本地 backend/frontend + Compose 管理的 MinIO/etcd/Milvus | 日常开发、联调、演示 |
| 手动 Web 联调 | `web/backend/main.py` + `web/frontend` | 同上 | 精细调试前后端 |
| 独立公众号标注 | `web/backend/wechat_annotator_main.py` | 前端 + 标注路由；不依赖主 RAG 栈 | 只做图片标注 |
| CLI / 实验脚本 | `rag_main.py`、`run_wechat_*`、`build_*`、`train_*`、`evaluate_*` | 视脚本而定 | 数据构建、实验、批处理 |
| 容器化验证 | `docker compose up -d minio etcd milvus backend frontend` | Docker Compose | 一体化容器验证 |

### 2.2 推荐方式：工作区根目录一键启动

当前最稳妥的方式是从工作区根目录启动，而不是直接在 `rag_qa/` 目录里手工拼装环境。

推荐入口：

- Windows 双击：`../start_edurag.bat`
- PowerShell：`../start_edurag.ps1`

启动器会负责：

- 使用 `rag_qa/.venv` 作为 Python 运行环境
- 通过 `docker compose` 启动 MinIO、etcd 和 Milvus
- 启动 FastAPI 后端和 Vite 前端
- 自动探测端口占用并处理常见冲突
- 启动完成后打开浏览器

默认优先端口及冲突回退策略：

| 服务 | 优先端口 | 近邻候选 | 随机回退区间 | 说明 |
| --- | --- | --- | --- | --- |
| Backend | 8000 | 8001/8002/8003 | 18000–18999（10 个） | 容器内仍是 8000 |
| Frontend | 5173 | 5174–5185 | 24000–24999（10 个） | 容器内仍是 5173 |
| MinIO API | 19000 | — | 29000–29149（12 个） | 容器内仍是 9000 |
| MinIO Console | 19001 | — | 29150–29299（12 个） | 容器内仍是 9001 |
| Milvus | 19530 | — | 29530–29699（12 个） | 容器内仍是 19530 |

启动器会把本次实际选中的端口写到 `rag_qa/logs/launcher/launcher-latest.log`，多项目并行时以日志里的结果为准。

> ⚠️ Milvus 端口被自动换到高位时，启动的是一个**全新的空 Milvus 容器**，不会自动复用占用 19530 的其它实例。如果 19530 上的外部 Milvus 才是你想用的（例如旧的 `milvus-standalone` 里有历史数据），请使用下面的「复用外部 Milvus」模式。

#### 复用外部 Milvus（可选）

在工作区根目录的 `.env` 里加：

```env
EDURAG_MILVUS_EXTERNAL_PORT=19530
```

启动器会跳过 docker compose 中 milvus/etcd 的拉起，仅启动 MinIO，并把 backend 连到指定端口上的外部 Milvus。启动前会检查该端口是否有服务监听，没有则立即报错。要恢复默认（本项目自管 Milvus），注释掉这一行即可。

### 2.3 手动开发方式

如果你不想用一键启动，也可以分别启动前后端。

后端：

```powershell
cd rag_qa\web\backend
..\..\.venv\Scripts\python.exe -m uvicorn main:app --reload --reload-dir ..\..\web\backend --reload-dir ..\..\core --reload-dir ..\..\base --host 0.0.0.0 --port 8000
```

如果你当前是在排查登录、路由、SSE 或页面联调稳定性，建议优先使用不带热重载的稳定模式：

```powershell
cd rag_qa\web\backend
..\..\.venv\Scripts\python.exe -m uvicorn main:app --host 0.0.0.0 --port 8000
```

前端：

```powershell
cd rag_qa\web\frontend
npm install
npm run dev -- --host 127.0.0.1 --port 5173
```

如果后端不在 `8000`，前端开发代理要显式改到实际端口：

```powershell
$env:VITE_API_PROXY_TARGET = 'http://127.0.0.1:8001'
cd rag_qa\web\frontend
npm run dev -- --host 127.0.0.1 --port 5173
```

### 2.4 命令行模式和脚本模式

如果你的目标不是 Web 联调，而是运行 RAG 脚本、命令行问答或数据处理脚本，可以直接在 `rag_qa/` 目录下使用：

```powershell
cd rag_qa
.venv\Scripts\python.exe rag_main.py
```

注意：凡是涉及知识入库、向量检索、知识库统计的脚本，都依赖 Milvus 可用。

### 2.5 独立公众号标注模式

如果当前工作只需要做公众号图片标注，不需要聊天、知识库、会话主链路，可以启动轻量后端入口：

```powershell
cd rag_qa\web\backend
..\..\.venv\Scripts\python.exe -m uvicorn wechat_annotator_main:app --reload --host 0.0.0.0 --port 8001
```

这个入口的特点：

- 只注册 `/api/wechat-annotator` 和 `/api/health`
- 不导入主 RAG 问答、知识库、会话堆栈
- 适合数据标注、图片说明补录、公众号工作台联调

### 2.6 容器化验证模式

虽然当前日常开发推荐“本地 backend/frontend + Compose 管理 MinIO/etcd/Milvus”的混合模式，但根目录 `docker-compose.yml` 也提供了 backend/frontend 容器定义，可用于容器化验证：

```powershell
cd ..
docker compose up -d minio etcd milvus backend frontend
```

注意：

- 这更适合环境验证和部署预演，不是当前首选开发方式。
- 容器化验证模式下，Milvus 已由同一份 Compose 拉起。

## 3. 当前依赖关系

### 3.1 基础设施依赖矩阵

| 依赖 | 当前用途 | 是否由根目录启动器负责 | 备注 |
| --- | --- | --- | --- |
| MinIO | 原始文件和对象存储 | 是 | 启动器会注入本地 MinIO 连接环境变量 |
| Etcd | Milvus standalone 元数据协调 | 是 | 由根目录 `docker-compose.yml` 启动 |
| Milvus | 知识入库、向量检索、知识库统计 | 是 | 当前工程启动器会自动起 Milvus |
| 本地模型目录 | BGE、BERT、Reranker 等模型加载 | 否 | 需保证 `rag_qa/models/` 及相关模型目录完整 |

### 3.2 一个容易踩坑的事实

当前工作区根目录的 `docker-compose.yml` 负责 MinIO、etcd 和 Milvus。

这意味着：

- 登录、基础页面、公众号标注等链路，在 MinIO 与后端就绪时通常可工作
- 知识入库、RAG 检索、知识库统计、部分问答能力，需要额外保证 Milvus 已正常启动并可连接
- 如果基础设施已由根目录工程版拉起但 Milvus 容器异常，仍会出现“检索失败”“知识库统计失败”

### 3.3 监控与生产覆盖文件

根目录还提供两个 Compose 覆盖文件：

| 文件 | 用途 | 备注 |
| --- | --- | --- |
| `../docker-compose.monitoring.yml` | 叠加 Prometheus + Grafana | 依赖已创建好的 `graduation-network` |
| `../docker-compose.prod.yml` | 生产环境覆盖 | 强制通过环境变量提供关键凭据，并关闭 MinIO 宿主机端口暴露 |

常见用法：

```powershell
cd ..
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d prometheus grafana
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

## 4. 环境与配置

### 4.1 Python 环境约定

当前项目默认使用 `rag_qa/.venv` 作为唯一 Python 运行环境。

快速自检：

```powershell
cd rag_qa
.venv\Scripts\python.exe -c "import sys; print(sys.executable)"
```

如果输出路径包含 `rag_qa\.venv`，说明环境正确。

### 4.1A 前端与容器版本基线

当前工程版联调和容器化验证，统一按下面的版本基线理解：

| 组件 | 最低要求 | 依据 |
| --- | --- | --- |
| Python | 3.8+ | 当前根 README、应用 README 与主技术文档统一口径 |
| Node.js | 18.x LTS | 前端容器镜像使用 `node:18-alpine`，本地开发建议与容器保持一致 |
| npm | 9+ | 当前 `web/frontend/package-lock.json` 使用 `lockfileVersion: 3` |
| Docker Desktop | 4.x+ | 当前工作区以 `docker compose` v2 作为默认编排命令 |

补充说明：

- 如果本机只有旧版 `docker-compose` 独立命令，而没有 `docker compose` v2，不视为当前默认开发环境达标。
- 如果本机 Node.js 低于 18，最常见影响是前端依赖安装和 Vite 本地联调行为与容器基线不一致。
- 如果你只记一条，优先记“本地环境尽量对齐容器基线”，即 Python 使用 `rag_qa/.venv`，Node.js 使用 18.x LTS，Compose 使用 v2。

### 4.2 配置优先级

当前配置读取规则是：

1. `EDURAG_*` 环境变量
2. `rag_qa/config.ini`
3. `rag_qa/base/config.py` 内部默认值

因此：

- 敏感信息优先放到 `.env`
- `config.ini` 保留非敏感默认配置或开发参数
- 不要把真实密钥写回仓库

### 4.3 需要准备的配置文件

环境变量模板：

- 工作区根目录：`../.env.example`
- 应用目录：`.env.example`

配置模板：

- `config.ini.template` -> `config.ini`

最小准备步骤：

```powershell
cd ..
Copy-Item .env.example .env

cd rag_qa
Copy-Item config.ini.template config.ini
```

## 5. VS Code 里推荐怎么跑

当前工作区已经配置了常用任务，优先用任务而不是随手开多个终端。

推荐任务：

- `Env: Self-check (.venv)`：检查 `.venv`、关键依赖和入口导入
- `Backend: Run Uvicorn (.venv)`：在正确环境下以收敛版热重载启动后端
- `Backend: Run Uvicorn Stable (.venv)`：以稳定模式启动后端，不启用热重载
- `Frontend: Run Vite`：启动前端开发服务器
- `Project: Run stable local app`：并行拉起稳定版后端和前端，适合本地联调
- `Repo: Self-check`：做仓库级自检
- `Release: Preflight Check`：发布或阶段提交前，串联环境、仓库、文档与关键运行文件检查
- `Project: Stop local services`：清理 8000/8001/5173/19000/19001/19530 等端口上的残留进程
- `Project: Docker down all`：关闭本地、监控、生产覆盖下可能残留的 Compose 服务
- `Project: Verify listening ports`：检查关键端口占用情况

如果当前这轮改动已经接近“可提交、可演示、可交付”，不要只跑环境自检；应额外执行一次 `Release: Preflight Check`，再进入人工验证前端页面、登录路径和演示链路。

开发服务稳定性说明：

- 当前 VS Code 后端任务默认设置 `EDURAG_DEV_FAST_STARTUP=1`，开发态会跳过 RAG 启动预热。
- 当前 `Backend: Run Uvicorn (.venv)` 只监视 `rag_qa/web/backend`、`rag_qa/core`、`rag_qa/base`，避免扫描整个工作区导致热重载抖动。
- 聊天、会话、知识库、数据集和测试集路由已切到按需加载 `rag_service`，降低每次 reload 的初始化压力。

演示前建议最少再确认 4 件事：

- 本次演示到底走哪条主链路，是否已经提前完整跑通过一次。
- 当前浏览器入口、前端端口和后端代理目标是否一致。
- 若要演示知识检索或知识库统计，Milvus 是否可用；若要演示文件链路，MinIO 是否可用。
- 如果主链路现场异常，是否已经准备好备选演示路径。

完整版本见 [../DEVELOPMENT_TEST_RELEASE_BASELINE.md](../DEVELOPMENT_TEST_RELEASE_BASELINE.md#L72) 的“演示验收清单”。

## 6. 常见工作流

### 6.1 Web 联调

推荐顺序：

1. 先确保 Docker Desktop 已启动
2. 启动根目录 `start_edurag.bat`，或手工起 MinIO/etcd/Milvus
3. 起后端
4. 起前端
5. 打开 `http://127.0.0.1:5173`

### 6.2 登录问题定位

当前前端登录态排错，优先看状态码：

- `401`：通常是工号或密码错误
- `404`：通常是前端代理没有指到正确后端，或后端没启动
- `Network Error`：通常是前端到后端网络链路没通

### 6.3 知识入库 / 检索验证

在跑知识入库、检索、知识库概览前，请先确认：

- Milvus 已可连接
- 模型目录存在
- `config.ini` 或环境变量中的 Milvus 配置正确

如果只是根目录工程版启动成功，不代表检索链路一定可用。

### 6.4 微信公众号链路

公众号相关功能不建议只看本文档，应该配合下面几份文档一起看：

- `微信公众号采集agent说明.md`
- `WECHAT_DESKTOP_AUTOMATION.md`
- `TECHNICAL_HANDBOOK.md` 中的微信链路章节

### 6.5 实验与评估脚本边界

当前仓库同时存在 Web 主链路脚本和实验/论文脚本，使用时请区分：

- `build_*`、`generate_*`、`train_*`、`evaluate_*` 主要服务于数据构建、训练和实验
- `ragas_paper_bundle/` 是论文/展示用数据、结果和图表目录，不等于官方 `ragas` 评估运行器
- `rag_assesment/` 主要保存历史生成数据集和中间产物
- 需要主系统联调时，优先回到 `main.py`、`rag_service.py`、前端页面和启动脚本

## 8. 常见问题

### 8.1 一键启动成功，但知识库功能报错

优先检查 Milvus，因为当前启动器虽然会自动起它，但容器异常、连接失败或集合状态异常仍会导致知识库链路报错。

### 8.2 前端打开了，但登录失败

优先确认：

- 后端是否真的在运行
- 前端代理是否仍指向 `8000`
- 如果后端实际在 `8001`，是否设置了 `VITE_API_PROXY_TARGET`

### 8.3 运行脚本时导入失败

优先确认你是不是在 `rag_qa/.venv` 里运行，而不是系统 Python 或其他环境。

### 8.4 启动端口被占用

优先用 VS Code 任务 `Project: Stop local services`，不要手工到处杀进程。如需查看本次启动器实际分配到的端口，看 `rag_qa/logs/launcher/launcher-latest.log` 里的 `Selected infrastructure ports` 行。

### 8.5 Milvus 报 `database itcast not found`

通常是因为本项目自管的 Milvus 是新拉起的空容器，而历史向量数据在另一套 Milvus（例如 19530 上的 `milvus-standalone`）里。处理方法：

- 若历史数据需要继续使用：在 `.env` 加 `EDURAG_MILVUS_EXTERNAL_PORT=19530`，重新启动
- 若可丢弃历史数据：在目标 Milvus 上创建 database 后重新 ingest

```powershell
.\rag_qa\.venv\Scripts\python.exe -c "from pymilvus import connections, db; connections.connect(host='127.0.0.1', port='19530'); print('exists' if 'itcast' in db.list_database() else db.create_database('itcast'))"
```
